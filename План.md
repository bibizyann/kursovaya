# План реализации проекта

План составлен на основе [`Диплом.md`](./Диплом.md) и уточнён [ADR 0006](docs/adr/0006-simulated-telemetry.md). Основной результат — Kubernetes-оператор и локальный стенд с синтетической телеметрией. Реальные драйверы, аппаратный Edge Agent и получение показаний внутри станка описываются только теоретически. K3s/KubeEdge и облако остаются дальнейшим развитием.

## Согласованная модель сборочного цеха

Предметная область описана в [модели сборочного цеха](docs/architecture/assembly-workshop.md) и закреплена в [ADR 0004](docs/adr/0004-assembly-workshop-model.md). Маршрут: нанесение пасты → установка SMD → оплавление → оптический контроль → ручной монтаж → программирование и функциональные испытания.

Базовый состав — шесть рабочих мест и восемь устройств: NeoDen YS350, NeoDen4, IN6, ND880, Weller WT1010M, STLINK-V3SET, Keysight E36312A и 34461A. Последние три устройства входят в одно место программирования и испытаний.

MVP работает полностью на симуляторах, без физического оборудования и моделирования движения плат. ПО и рецепты меняются последовательно по рабочим местам; при неудаче требуется автоматическое восстановление затронутых мест на ранее принятой ревизии. Механизм восстановления ещё предстоит согласовать с GitOps; правила владения состоянием из ADR 0002 сохраняются.

Сейчас реализованы каталог восьми устройств, учебные рецепты A/B, симуляторы характерных операций и новые шаблоны размещения (см. [ADR 0005](docs/adr/0005-equipment-simulation.md)). Последовательный переход, автоматическое восстановление и совместный сценарий трёх тестовых приборов ещё предстоит реализовать. Для мониторинга реализован этап 1: контракт снимков, валидация и примеры восьми устройств. Приёмник, периодическая генерация, MQTT и графики ещё не реализованы. Следующий этап — приёмник в памяти и экспорт метрик без MQTT. Инвентарь пока встроен в Go-каталог, численные параметры рецептов являются учебными примерами.

## Целевая архитектура

```text
UI -> Factory API -> Git -> Argo CD -> TechProcess -> Go Operator
                                                       |
                                                       +-> Deployment / DaemonSet / ConfigMap
                                                       +-> TechProcess.status
                                                       +-> /metrics -----------------------+
                                                                                           |
Equipment Simulator -> MQTT -> Mosquitto -> Go Telemetry Receiver -> /metrics -> Prometheus -> Grafana
```

UI, Factory API и GitOps-интеграция — целевые компоненты отдельного направления. Для локальных тестов по-прежнему допускается прямое применение CR. Канал мониторинга начинается с готового сообщения внешней программы; в стенде его формирует симулятор.

Границы ответственности:

- Git задаёт желаемое состояние; Argo CD управляет CR, оператор — производными ресурсами.
- MQTT передаёт только наблюдаемое состояние. Приёмник не меняет CR или workload.
- Mosquitto, приёмник, Prometheus и Grafana — компоненты платформы, независимые от жизненного цикла отдельного `TechProcess`.
- В симуляторе подготовка, калибровка и исправность определяют readiness. Недоступность мониторинга не останавливает исправное приложение.
- Приёмник хранит текущие снимки в памяти. Пропуски при разрыве связи не восстанавливаются, постоянная очередь и производственная БД не требуются.
- Подробнее о полях, единицах и обработке повторов — в [контракте телеметрии](docs/architecture/telemetry.md).

## Важные уточнения к исходному документу

1. На одном edge-узле следует выбирать либо `k3s agent`, либо `KubeEdge EdgeCore`, а не устанавливать их как два параллельных исполнительных слоя. Для разработки используется Kind согласно [ADR 0001](docs/adr/0001-runtime-topology.md), затем проводится отдельный spike `K3s control-plane + CloudCore + 1 EdgeCore`.
2. Для HA-профиля нужны минимум три K3s server-узла с embedded etcd и фиксированный адрес API.
3. `TargetNodes []string` следует заменить на `metav1.LabelSelector`.
4. Автовосстановление возможно только на узле с таким же физическим оборудованием. Если резерва нет, корректное состояние — `Degraded`.
5. Для драйверов эксклюзивного оборудования нельзя использовать rollout с двумя одновременно работающими pod. Нужен `Recreate` либо staged rollout с безопасной остановкой.
6. HPA применим только к stateless-сервисам обработки данных.
7. Yandex IoT Core не следует закладывать в новую реализацию. Вместо него используется Mosquitto на VM или в Managed Kubernetes.

Пример capability-меток текущего многоузлового стенда (конкретные наборы на узлах см. в `infra/kind/cluster.yaml`):

```text
factory.local/line=line-one
factory.local/paste-printing=true
factory.local/programming-test=true
factory.local/spare-group=line-one
```

## Этапы реализации мониторинга

После каждого этапа работа останавливается до явного ОК пользователя на следующий. Оценки сроков из исходного плана больше не используются для упрощённого мониторинга.

| Этап | Изменения | Критерий готовности | Состояние |
|---|---|---|---|
| 1. Границы и контракт | ADR 0006, согласованные документы, `internal/telemetry`, типы, валидация и восемь JSON-примеров | Все типы устройств имеют валидные примеры; пакет независим от Kubernetes/MQTT/Prometheus | Реализован |
| 2. Приёмник и exporter | `internal/telemetryreceiver`: последние снимки, порядок сообщений, ожидаемые устройства, свежесть, Prometheus collector | Повторы, смена экземпляра, отсутствие и устаревание данных проверяются без брокера | Не начат |
| 3. Генератор | `internal/simulator/generator.go`, `telemetry.go`, параметры интервала и seed; общее состояние с HTTP API | Повторяемые значения и согласованные readiness/счётчики при управляемых отказах | Не начат |
| 4. MQTT | `internal/telemetrymqtt`, `cmd/telemetry-receiver`, подключение и подписки, ограниченная отправка без постоянной очереди | Один симулятор передаёт данные через Mosquitto на `/metrics`; после разрыва приходят новые снимки | Не начат |
| 5. Метрики оператора | `internal/controller/metrics.go`, Conditions, workload counts, время rollout из status; проверка готовности новой ревизии | Повторные Reconcile и перезапуск не искажают длительность завершённого rollout | Не начат |
| 6. Полный Kind-стенд | Образ приёмника, `config/telemetry`, параметры A/B, Make targets и CI | Все восемь устройств публикуют данные; инфраструктура мониторинга переживает A → B | Не начат |
| 7. Prometheus и Grafana | `config/monitoring`, закреплённый chart, ServiceMonitors, правила и три provisioned dashboard | Данные отображаются без ручной настройки; отсутствие данных отличается от нуля | Не начат |
| 8. Сквозная проверка | e2e-сценарии, runbook, CSV/JSON результатов экспериментов | Проверены A/B, fault, uncalibrated, MQTT outage, перезапуски и повторы | Не начат |

Первая сквозная цепочка появляется после этапа 4. Полный визуальный стенд — после этапа 7. Узкие unit-тесты добавляются вместе с кодом каждого этапа, а не откладываются на конец. `make test-unit` уже включает контракт телеметрии.

## Другие направления проекта

Эти работы не включаются автоматически в этапы мониторинга:

- последовательное обновление рабочих мест и автоматический rollback с сохранением прогресса и соблюдением Git ownership;
- развитие критериев Ready для одной целевой ревизии, timeout и безопасного удаления в операторе;
- Factory API/UI, GitOps-репозиторий, Argo CD и локальный registry;
- согласованный сценарий трёх приборов испытаний, если он понадобится для демонстрации оператора;
- опциональный K3s/KubeEdge pilot после отдельной проверки совместимости;
- опциональное облако для сводной аналитики и резервирования.

Реальные аппаратные интеграции, локальный gRPC, last-known-good конфигурация и store-and-forward остаются теоретическим описанием или отдельным будущим расширением. Требование реализации аппаратного Edge Agent из раннего плана отменено ADR 0006.

## Модель CRD

Текущие типы находятся в [api/v1alpha1](api/v1alpha1/techprocess_types.go). `TechProcess` задаёт шаблон, selector, параметры, rollout и timeout; status содержит Conditions с `observedGeneration`, применяемую ревизию, готовность компонентов и время обновления.

Мониторинг использует существующие `args` и `env` компонентов `TechProcessTemplate`; новый CRD не нужен. Идентичность устройства и рабочего места в телеметрии берётся из каталога, а не из Kubernetes node name. Телеметрия не записывает каждую точку в status CR.

Целевая готовность относится к одной ревизии и включает readiness workload, исправность, подготовку и применимую проверку калибровки. В текущем симуляторе эти проверки объединены в `/readyz`; оператор собирает готовность workloads. Проверка отсутствия ложного Ready старой ревизии входит в этап 5. Ни MQTT, ни Prometheus не становятся каналом принятия решений о готовности.

Helm используется для установки компонентов платформы. Оператор создаёт дочерние ресурсы напрямую; Helm не вызывается внутри Reconcile.

## Структура проекта

```text
cmd/main.go                         # существующий оператор
cmd/equipment-simulator/            # существующий симулятор
cmd/telemetry-receiver/             # этап 4
api/v1alpha1/                       # существующие CRD
internal/controller/                # оператор и его метрики на этапе 5
internal/workload/                  # генерация Kubernetes-ресурсов
internal/equipment/                 # каталог и учебные рецепты
internal/simulator/                 # HTTP API; генератор на этапе 3
internal/telemetry/                 # реализованный контракт и fixtures
internal/telemetryreceiver/         # этап 2
internal/telemetrymqtt/             # этап 4
config/telemetry/                   # этап 6
config/monitoring/                  # этап 7
infra/kind/                         # локальный стенд
test/e2e/                           # существующие тесты; расширение на этапе 8
docs/{architecture,adr,runbooks}/
```

Один Go-модуль сохраняется. Для контракта используются стандартная библиотека и чистый каталог оборудования. MQTT-библиотека добавляется на этапе 4; Prometheus client используется в приёмнике и операторе. Go API Kubernetes остаётся в подсистемах, которым нужен доступ к кластеру.

## Что не включать в MVP

- Kafka и Flux;
- одновременно Loki и EFK;
- Longhorn без трёх подходящих storage-нод;
- полноценное обучение ML-модели;
- HPA для hardware-bound драйверов;
- canary/blue-green на одном физическом устройстве;
- прямое управление производством из облака;
- реальные аппаратные драйверы, аппаратный Edge Agent и локальный gRPC;
- постоянную очередь bbolt, replay истории и гарантию нулевой потери телеметрии;
- PostgreSQL или другую производственную БД, сквозной учёт плат и расчёт OEE;
- собственное кэширование pod-манифестов.

## Приёмочные метрики

Предварительные цели, которые нужно уточнить после baseline:

- p95 перенастройки с локально доступными образами — не более 5 минут;
- сокращение медианного времени относительно ручного сценария — не менее 70%;
- восстановление после падения pod — p95 не более 90 секунд;
- восстановление после отказа узла при наличии совместимого резерва — не более 5 минут;
- неправильных размещений и ложных `Ready` — 0;
- отображение изменения состояния в UI — p95 не более 15 секунд;
- отсутствие телеметрии отражается как unknown; после восстановления MQTT поступают новые снимки без повторного увеличения счётчиков;
- недоступность мониторинга не меняет аппаратную readiness симулятора;
- 24–72-часовой прогон — без зависших CR и невосстановленных отказов.

Цели времени относятся к программному стенду и требуют baseline; синтетические показания не доказывают характеристики реального производства. Для экспериментальной части желательно выполнить не менее 20 ручных и 20 автоматизированных перенастроек и по 10 повторов каждого ключевого отказа. Сохранять нужно не только скриншоты Grafana, но и исходные результаты измерений.

## Итоговый комплект проекта

- три Go-бинарника стенда мониторинга: operator, equipment-simulator, telemetry-receiver; Factory API — отдельное направление;
- CRD, RBAC и sample-манифесты;
- два шаблона техпроцесса;
- Helm-чарт платформы и GitOps-конфигурация;
- CI pipeline и контейнерные образы;
- dashboards и alerts;
- unit, envtest, e2e и fault-тесты;
- runbooks и воспроизводимый отчёт с измерениями.
