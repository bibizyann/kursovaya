# План реализации проекта

План составлен на основе [`Диплом.md`](./Диплом.md). Оптимальный путь — сначала собрать защищаемый локальный MVP, затем перенести его на отказоустойчивый K3s/KubeEdge-стенд и только после этого добавлять облако.

## Целевая архитектура

```text
Web UI
  │
  ▼
Go Factory API ──commit──► GitOps-репозиторий
  │                              │
  │ read status                  ▼
  │                          Argo CD
  │                              │
  ▼                              ▼
Kubernetes API ◄────────── TechProcess CR
  │
  ▼
Go Operator
  │
  ├── Deployment / DaemonSet / ConfigMap
  ├── размещение по capability-меткам
  └── TechProcess.status
          │
          ▼
K3s agent или KubeEdge EdgeCore
          │
          ├── Go Edge Agent ──local gRPC── оборудование
          └── MQTT ──► Mosquitto ──► Prometheus/Grafana
```

Границы ответственности:

- Git — единственный источник желаемого состояния.
- Backend записывает изменения в Git, но имеет только read-доступ к Kubernetes.
- Argo CD управляет объектами `TechProcess` и конфигурацией платформы.
- Оператор единолично создаёт дочерние workload-ресурсы.
- MQTT используется для телеметрии, gRPC — локально для работы с оборудованием, Kubernetes/GitOps — для смены техпроцесса.
- Edge Agent не дублирует kubelet или EdgeCore: он отвечает только за оборудование, калибровку, last-known-good конфигурацию и локальный буфер.

## Важные уточнения к исходному документу

1. На одном edge-узле следует выбирать либо `k3s agent`, либо `KubeEdge EdgeCore`, а не устанавливать их как два параллельных исполнительных слоя. Для разработки используется k3d/K3s, затем проводится отдельный spike `K3s control-plane + CloudCore + 1 EdgeCore`.
2. Для HA-профиля нужны минимум три K3s server-узла с embedded etcd и фиксированный адрес API.
3. `TargetNodes []string` следует заменить на `metav1.LabelSelector`.
4. Автовосстановление возможно только на узле с таким же физическим оборудованием. Если резерва нет, корректное состояние — `Degraded`.
5. Для драйверов эксклюзивного оборудования нельзя использовать rollout с двумя одновременно работающими pod. Нужен `Recreate` либо staged rollout с безопасной остановкой.
6. HPA применим только к stateless-сервисам обработки данных.
7. Yandex IoT Core не следует закладывать в новую реализацию. Вместо него используется Mosquitto на VM или в Managed Kubernetes.

Пример меток узлов:

```text
factory.local/line=line-1
factory.local/camera=true
factory.local/tester=model-x
factory.local/spare-group=tester-a
```

## Поэтапный план

| Этап | Срок | Работы | Критерий готовности |
|---|---:|---|---|
| 0. Формализация требований | 3–4 дня | Зафиксировать сценарий `board-a → board-b`, состав узлов, состояния линии, SLO, границы real-time, baseline ручной перенастройки. Оформить ADR по GitOps, K3s/KubeEdge, MQTT и владению ресурсами | Есть схема архитектуры и матрица «требование → тест → метрика» |
| 1. Инициализация проекта | 1 неделя | Один Go-модуль, Kubebuilder, Makefile, Dockerfile, локальный k3d-кластер с 3 worker-нодами, registry, базовый GitLab CI | `make dev-up` поднимает стенд, оператор устанавливается, pipeline проходит |
| 2. Симулятор производства | 1 неделя | Написать на Go симуляторы камеры и тестового стенда. Добавить режимы: нормальная работа, задержка, ошибка, потеря связи, неуспешная калибровка. Подготовить профили двух изделий | Техпроцессы A и B вручную разворачиваются на размеченных узлах |
| 3. CRD и доменная модель | 1 неделя | Создать `TechProcess` и `TechProcessTemplate`, OpenAPI/CEL-валидацию, RBAC, sample-манифесты | Валидный CR принимается, некорректный отклоняется |
| 4. Оператор Kubernetes | 2 недели | Идемпотентный Reconcile, `CreateOrPatch`/SSA, owner references, finalizer, affinity, taints/tolerations, probes, revision hash, Events, status conditions | Создание CR разворачивает нужные workload только на совместимых узлах |
| 5. Конечный автомат и rollback | 1 неделя | Состояния `Progressing`, `Ready`, `Degraded`; `observedGeneration`; readiness оборудования и калибровки; timeout; last-known-good revision; безопасное удаление | Ошибочный релиз не получает `Ready`, предыдущая версия восстанавливается |
| 6. GitOps и CI/CD | 1–1,5 недели | Argo CD, отдельный config-репозиторий, Harbor, immutable image tags/digests. Pipeline: lint → unit/envtest → e2e → build → scan → push → update config | Commit приводит к обновлению `TechProcess`; Git revert выполняет rollback |
| 7. Edge Agent | 1–1,5 недели | `HardwareDriver` с реализациями fake, затем OPC-UA/Modbus; локальный gRPC API; health/calibration; атомарный last-known-good cache | Агент продолжает текущий процесс при потере control-plane |
| 8. Телеметрия | 1 неделя | Mosquitto, Paho MQTT, QoS 1, retained status, sequence ID, дедупликация, локальная очередь bbolt, backoff/jitter | После сетевого разрыва накопленные события доставляются без потерь в пределах буфера |
| 9. Backend и UI | 1–1,5 недели | Go `net/http`, `html/template` и статический JS; каталог процессов; активация, статус узлов, причины ошибки, rollback; SSE для обновлений; аудит действий | Диспетчер переключает A → B из UI и наблюдает достижение `Ready` |
| 10. Наблюдаемость и безопасность | 1–1,5 недели | Метрики оператора и агента, Prometheus, Grafana, Alertmanager, Loki; RBAC, NetworkPolicy, mTLS, Secrets, non-root-контейнеры, сканирование образов | Каждый тестовый отказ виден в UI/Grafana и вызывает ожидаемый alert |
| **Граница MVP** | **10–12 недель** | Локальный кластер, симуляторы, оператор, UI, GitOps, MQTT и мониторинг | Полный демонстрационный сценарий без физического оборудования и облака |
| 11. Pilot K3s/KubeEdge | 2 недели | Три K3s server-ноды, CloudCore, EdgeCore на edge-хостах, Harbor, NFS; local-path для edge-буфера; backup/restore | Потеря одного control-plane не нарушает quorum; отключённый edge продолжает last-known-good процесс |
| 12. Эксперименты ВКР | 1–1,5 недели | Смена A/B, плохой образ, pod crash, node failure, потеря MQTT/control-plane/интернета, переполнение буфера, rollback, длительный прогон | Получены сырые CSV/JSON, графики, медиана и p95 по всем метрикам |
| 13. Облачное расширение | 1–2 недели, опционально | Terraform для Yandex Managed Kubernetes, Container Registry, IAM и Mosquitto; репликация образов и сводный Grafana | Отключение облака не влияет на локальное управление линией |
| 14. Финальная поставка | 3–5 дней | Installation guide, runbooks, ADR, OpenAPI/protobuf, backup-инструкция, demo script, ограничения прототипа, release tag | Проект разворачивается на чистом стенде по документации |

Критический путь:

```text
требования → CRD → оператор → безопасный rollout → GitOps
→ Edge Agent/MQTT → UI → pilot → эксперименты → оформление
```

## Рекомендуемая модель CRD

Минимальные поля `TechProcess`:

```go
type TechProcessSpec struct {
    TemplateRef    corev1.LocalObjectReference `json:"templateRef"`
    TargetSelector metav1.LabelSelector        `json:"targetSelector"`
    Parameters     map[string]string            `json:"parameters,omitempty"`
    Rollout        RolloutSpec                  `json:"rollout,omitempty"`
    Timeout        metav1.Duration              `json:"timeout,omitempty"`
}

type TechProcessStatus struct {
    ObservedGeneration int64              `json:"observedGeneration,omitempty"`
    Conditions         []metav1.Condition `json:"conditions,omitempty"`
    AppliedRevision    string             `json:"appliedRevision,omitempty"`
    DesiredNodes       int32              `json:"desiredNodes,omitempty"`
    ReadyNodes         int32              `json:"readyNodes,omitempty"`
    NodeStatuses       []NodeStatus       `json:"nodeStatuses,omitempty"`
    StartedAt          *metav1.Time       `json:"startedAt,omitempty"`
    CompletedAt        *metav1.Time       `json:"completedAt,omitempty"`
}
```

`Ready` должен учитывать одновременно:

- pod запущен;
- readiness-проба пройдена;
- оборудование доступно;
- калибровка успешна;
- на всех обязательных узлах применяется одна revision.

Helm в MVP используется для упаковки платформы и каталога `TechProcessTemplate`. Оператор создаёт дочерние ресурсы напрямую. Это исключает одновременное управление одними workload со стороны Argo CD и Helm SDK внутри оператора.

## Структура репозиториев

```text
factory-platform/
├── cmd/{operator,factory-api,edge-agent,equipment-simulator}/
├── api/production/v1alpha1/
├── internal/{controller,workload,drivers,telemetry,gitops}/
├── proto/
├── web/
├── config/                 # Kubebuilder CRD/RBAC
├── charts/                 # установка платформы и каталог
├── infra/{k3d,ansible,terraform}/
├── observability/
├── tests/{unit,e2e,fault,experiments}/
└── docs/{adr,runbooks,experiments}/

factory-config/
├── environments/{lab,pilot}/
├── catalog/{board-a,board-b}/
└── active/line-1.yaml
```

Основной Go-стек:

- `controller-runtime`, `client-go`, Kubebuilder;
- `net/http`, `html/template`, SSE;
- `grpc-go`, Protobuf;
- `paho.mqtt.golang`, `bbolt`;
- `client_golang`;
- `gopcua/opcua`, `goburrow/modbus`;
- `envtest`, k3d/kind для интеграционных тестов.

## Что не включать в MVP

- Kafka и Flux;
- одновременно Loki и EFK;
- Longhorn без трёх подходящих storage-нод;
- полноценное обучение ML-модели;
- HPA для hardware-bound драйверов;
- canary/blue-green на одном физическом устройстве;
- прямое управление производством из облака;
- собственное кэширование pod-манифестов в Edge Agent.

## Приёмочные метрики

Предварительные цели, которые нужно уточнить после baseline:

- p95 перенастройки с локально доступными образами — не более 5 минут;
- сокращение медианного времени относительно ручного сценария — не менее 70%;
- восстановление после падения pod — p95 не более 90 секунд;
- восстановление после отказа узла при наличии совместимого резерва — не более 5 минут;
- неправильных размещений и ложных `Ready` — 0;
- отображение изменения состояния в UI — p95 не более 15 секунд;
- потеря телеметрии при разрыве в пределах ёмкости буфера — 0;
- 24–72-часовой прогон — без зависших CR и невосстановленных отказов.

Для экспериментальной части желательно выполнить не менее 20 ручных и 20 автоматизированных перенастроек и по 10 повторов каждого ключевого отказа. Сохранять нужно не только скриншоты Grafana, но и исходные результаты измерений.

## Итоговый комплект проекта

- четыре Go-бинарника: operator, factory-api, edge-agent, equipment-simulator;
- CRD, RBAC и sample-манифесты;
- два шаблона техпроцесса;
- Helm-чарт платформы и GitOps-конфигурация;
- CI pipeline и контейнерные образы;
- dashboards и alerts;
- unit, envtest, e2e и fault-тесты;
- runbooks и воспроизводимый отчёт с измерениями.
