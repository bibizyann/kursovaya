# План реализации практической части ВКР

## Тема: Информационная система автоматизированного управления жизненным циклом ПО на распределённых вычислительных узлах сборочного цеха на базе операторов Kubernetes

---

## 1. Обоснование актуальности и анализ существующих решений

### 1.1 Актуальность технологии

Переход от Индустрии 3.0 (жёсткая автоматизация: ПЛК + SCADA) к Индустрии 4.0/5.0 требует гибкости под мелкосерийное и позаказное производство.

Ключевые тезисы:

- Рост доли мелкосерийных/кастомизированных производств → частая смена техпроцессов → традиционные системы перестраиваются вручную (дни/недели).
- Рост числа программно-управляемых узлов на цехе (камеры контроля качества, роботы, тестовые стенды) требует унифицированного способа развёртывания и обновления ПО.
- Edge-computing снижает задержки и зависимость от связи с облаком/ЦОД, но порождает проблему управления множеством разнородных узлов — это и решает оркестрация Kubernetes.

### 1.2 Анализ существующих решений

|Класс решений|Примеры|Ограничения|
|---|---|---|
|Классические SCADA/MES|Siemens SIMATIC, Schneider Electric, Rockwell FactoryTalk|Централизация, единая точка отказа, ручная перенастройка, слабая поддержка контейнеризации, долгий цикл обновления ПО|
|Промышленные IoT-облачные платформы|Siemens MindSphere, PTC ThingWorx|Зависимость от облака/канала связи, задержки, не решают задачу edge-развёртывания ПО|
|Edge-K8s платформы общего назначения|KubeEdge, K3s, Azure IoT Edge|Есть база оркестрации, но нет готовой интеграции под задачи именно сборочного цеха с быстрой сменой техпроцесса|

### 1.3 Вывод

Предлагаемое решение — не изобретение новой оркестрации, а **адаптация связки K3s/KubeEdge + GitOps под конкретный производственный сценарий**, с готовым набором Helm-шаблонов техпроцессов. Преимущество — в **скорости перестройки** и **отказоустойчивости** по сравнению с ручной перенастройкой SCADA/ПЛК.

Критерии оценки эффективности (без учёта стоимости внедрения):

- время перенастройки линии под новое задание;
- время восстановления после сбоя узла;
- доступность системы (uptime);
- процент простоя оборудования при смене номенклатуры.

## 2. Производство и суть решения

**Кейс**: цех мелкосерийной сборки и функционального тестирования кастомных электронных модулей (SMD-монтаж, контроль пайки машинным зрением, функциональный тест плат).

Обоснование выбора: часто меняющаяся номенклатура, разные тестовые профили под разные платы, задействовано машинное зрение — удобно иллюстрировать смену ПО на узлах.

**Суть решения**: при смене производственного задания меняется не физическое оборудование, а **набор контейнеризированных сервисов**, разворачиваемых оркестратором на нужных узлах:

- драйверы под конкретное тестовое оборудование;
- модель машинного зрения под конкретный тип платы;
- конфигурация протоколов связи и параметров контроля качества.

Перестройка линии занимает минуты вместо часов/дней ручной перенастройки.

## 3. Узлы, ПО на них и взаимодействие

### 3.1 Edge-узлы (рабочие места), под управлением K3s/KubeEdge EdgeCore

- драйверы оборудования (OPC-UA/Modbus адаптеры к тестовым стендам, паяльным станциям);
- сервис машинного зрения (контроль качества пайки/сборки);
- сервис сбора телеметрии (Node Exporter, Telegraf);
- локальный буфер данных на случай разрыва связи с центром.

### 3.2 Control-plane цеха (локально, 3 узла для отказоустойчивости)

- API Server / etcd / Scheduler / Controller Manager;
- GitOps-контроллер (Argo CD/Flux) — синхронизация манифестов;
- система управления производственными заданиями (Job Orchestrator, интеграция с MES/ERP);
- мониторинг (Prometheus + Grafana), логирование (Loki/EFK);
- Harbor — приватный registry образов.

### 3.3 Шлюзовые узлы

- Ingress-контроллер;
- защищённый канал (VPN/mTLS) между цехом и облаком (CloudCore в терминах KubeEdge).

### 3.4 Хранилище

- Longhorn/NFS для персистентных данных (снимки дефектов, логи тестов, конфигурации).

### 3.5 Взаимодействие узлов (сценарий)

1. Изменение производственного задания → коммит манифеста в Git.
2. GitOps-контроллер видит diff → применяет манифесты на нужных edge-узлах (через nodeSelector/affinity, привязывающий поды к конкретному физическому оборудованию).
3. Edge-узлы отчитываются о статусе через MQTT/Kafka.
4. Мониторинг отражает готовность линии в реальном времени.

## 4. Управление ПО: применение Kubernetes и оркестрации

### 4.1 Топология: локально или в облаке

Гибридная схема:

- **Локально (K3s/KubeEdge)** — основной контур управления. Отвечает за real-time развёртывание ПО на edge-узлах и реакцию на сбои. Обязателен, так как критична низкая задержка, независимость от интернет-канала цеха и требования к тому, чтобы производственные данные не покидывали периметр предприятия.
- **В облаке (Yandex Cloud Managed Service for Kubernetes)** — вторичный, необязательный уровень: централизованный мониторинг по нескольким цехам/площадкам, резервное хранение Git-репозитория манифестов и Container Registry, обучение/обновление ML-моделей контроля качества, удалённый доступ инженеров.

Обоснование: Managed Service for Kubernetes в Yandex Cloud берёт на себя администрирование master-узла, диагностику и восстановление нод, интеграцию с Yandex Container Registry и IAM, автоскейлинг и провижининг через Terraform — то есть удобен именно для верхнего, не критичного к задержкам уровня, а не для контура реального времени на полу цеха.

### 4.2 Контейнеризация

Каждый программный компонент (драйвер, тестовый сервис, ML-модель контроля) — отдельный Docker-образ, версионируется в Harbor (локально) с опциональной репликацией в Yandex Container Registry.

### 4.3 Декларативное управление (GitOps)

Манифесты (Deployment, DaemonSet, ConfigMap, Secret) в Git — единый источник истины. Смена техпроцесса = коммит нового Helm-чарта/Kustomize-оверлея → Argo CD автоматически синхронизирует кластер.

### 4.4 Планирование размещения

nodeSelector/nodeAffinity/taints-tolerations — привязка конкретных подов к конкретным физическим рабочим местам, оснащённым нужным оборудованием (например, под с моделью машинного зрения — только на узел с подключённой камерой).

### 4.5 Сценарий быстрой перестройки

1. Диспетчер выбирает новый техпроцесс в UI.
2. Система коммитит соответствующий Helm-релиз в Git.
3. Argo CD фиксирует diff и применяет изменения.
4. Старые поды завершаются gracefully (rolling update), новые разворачиваются и проходят readiness-пробы.
5. Как только все задействованные узлы готовы — линия открыта для нового заказа.

### 4.6 Отказоустойчивость

Liveness/readiness probes, автоматическое перепланирование подов при отказе узла, уведомление диспетчера.

### 4.7 CI/CD

Pipeline (GitLab CI/Jenkins) → сборка образа → тесты в staging namespace → canary/blue-green выкатка на edge, чтобы не останавливать всё производство разом.

### 4.8 Наблюдаемость

Prometheus + Grafana — дашборды состояния в реальном времени; Alertmanager — уведомления; Loki/EFK — централизованные логи.

### 4.9 Масштабирование

HPA для сервисов обработки данных (например, рост потока изображений с камер контроля).

### 4.10 Безопасность

RBAC по цехам/линиям, NetworkPolicy для изоляции трафика между техпроцессами, mTLS между control-plane и edge.

## 5. Итоговое решение

Результат — информационная система с веб-панелью диспетчера, объединяющей:

- каталог шаблонов техпроцессов (Helm-чарты) для быстрого выбора нового задания;
- одно действие для инициации переразвёртывания ПО на нужных edge-узлах;
- дашборд готовности каждого рабочего места в реальном времени (под запущен / healthcheck пройден / оборудование откалибровано);
- телеметрию производства (процент брака, время цикла);
- автоматическое восстановление после сбоев узлов/оборудования;
- опциональный облачный уровень (Yandex Cloud) для сводной аналитики по нескольким площадкам.

## 6. Пошаговый план реализации на Go

Основной управляющий софт (оператор Kubernetes, edge-агент, backend диспетчерской панели) пишется на Go — это стандартный язык экосистемы Kubernetes (client-go, controller-runtime, kubebuilder написаны и рассчитаны именно на него).

### Шаг 1. Инициализация проекта оператора

```bash
kubebuilder init --domain factory.local --repo factory.local/tech-process-operator
kubebuilder create api --group production --version v1 --kind TechProcess
```

### Шаг 2. Определение CRD `TechProcess`

```go
type TechProcessSpec struct {
    TargetNodes   []string          `json:"targetNodes"`
    HelmChartRef  string            `json:"helmChartRef"`
    Parameters    map[string]string `json:"parameters,omitempty"`
}

type TechProcessStatus struct {
    Phase        string   `json:"phase"` // Pending, Deploying, Ready, Failed
    ReadyNodes   []string `json:"readyNodes,omitempty"`
}
```

### Шаг 3. Реализация Reconcile-цикла оператора

```go
func (r *TechProcessReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
    var tp productionv1.TechProcess
    if err := r.Get(ctx, req.NamespacedName, &tp); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }
    // рендер Helm-чарта под tp.Spec.HelmChartRef и Parameters
    // применение Deployment/DaemonSet с nodeAffinity на tp.Spec.TargetNodes
    // обновление tp.Status по readiness подов
    return ctrl.Result{}, nil
}
```

### Шаг 4. Edge Agent (демон на каждом узле)

- на базе `client-go` informer'ов отслеживает назначенные поду конфигурации;
- при разрыве связи с control-plane использует локальный кэш последней конфигурации;
- реализует интерфейс `HardwareDriver` для конкретного тестового стенда/камеры.

### Шаг 5. Обмен телеметрией

- gRPC-сервис (`google.golang.org/grpc`) между edge-агентом и control-plane для команд управления;
- MQTT-клиент (`eclipse/paho.mqtt.golang`) для потоковой телеметрии (в т.ч. публикация в Yandex IoT Core при гибридной схеме).

### Шаг 6. Backend диспетчерской панели

- HTTP API на Go (`net/http` + `gin`/`echo`);
- создаёт/обновляет объекты `TechProcess` через `client-go` по действиям диспетчера в UI.

### Шаг 7. CI/CD

- сборка Go-бинарников в контейнеры (multi-stage Dockerfile);
- публикация образов в Harbor (и опционально в Yandex Container Registry);
- обновление через Argo CD.

### Шаг 8. Тестирование

- unit-тесты оператора через `envtest`;
- интеграционные тесты на `kind`/`k3d`, имитирующие несколько edge-узлов.

### Шаг 9. Деплой и проверка

```bash
make manifests && make install && make deploy IMG=harbor.local/tech-process-operator:v0.1
kubectl apply -f config/samples/production_v1_techprocess.yaml
kubectl get techprocess -w
```

### Шаг 10. Мониторинг оператора

- экспорт метрик через `client_golang` (Prometheus) — количество успешных/неуспешных Reconcile, среднее время перестройки линии.

## 7. Интеграция с Yandex Cloud (гибридный вариант)

Если по решению используется облачный верхний уровень:

- **Yandex Managed Service for Kubernetes** — центральный кластер для агрегирующих сервисов: сводный Argo CD/Grafana по нескольким цехам, обучение ML-моделей контроля качества, резервный Container Registry.
- **Yandex IoT Core** — MQTT-брокер для передачи телеметрии с edge-узлов в облако, когда нужен сводный анализ по нескольким площадкам; поддерживает работу через gRPC/Protobuf и постоянные топики на случай нестабильной связи.
- **Yandex Container Registry** — резервное/центральное хранилище образов, интегрируется с Managed K8s через сервисные аккаунты.
- **Terraform-провайдер Yandex Cloud** — декларативное описание облачной инфраструктуры (кластер, реестр, сервисные аккаунты) в том же GitOps-подходе, что и локальные манифесты.

Важно: критический контур принятия решений (развёртывание ПО на конкретный станок, реакция на сбой) остаётся на локальном K3s/KubeEdge — облако используется только для агрегации, аналитики и резервирования, не для управления в реальном времени.
