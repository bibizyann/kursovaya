# Симуляторы оборудования сборочного цеха

Реализованы восемь программных моделей выбранных устройств. Подключение к физическим станкам, их фирменным API и интерфейсам SCPI описывается только теоретически. Каталог, рецепты и вычисление результатов находятся в `internal/equipment/catalog.go`; HTTP-обёртка — в `internal/simulator`.

## Запуск одного устройства

```bash
make build-simulator
./bin/equipment-simulator --list-equipment
./bin/equipment-simulator --equipment=reflow-oven-01 --product=board-a --listen=:8080
```

В другом терминале:

```bash
curl -sS localhost:8080/api/v1/status
curl -sS -X POST localhost:8080/api/v1/operations
```

Статус содержит модель, рабочее место, рецепт, ревизию и готовность. Результат операции содержит `equipmentId`, `workstation`, `product`, `recipeId`, `revision`, `sequence`, `accepted` и характерные для устройства `readings`. В Kubernetes ревизия берётся из `FACTORY_REVISION`, которую задаёт оператор; при отдельном запуске — из `--revision` или значения `standalone`.

По умолчанию запускается `optical-inspector-01`. Ошибочный ID, неизвестный продукт или одновременное указание `--equipment` и `--kind` приводят к ошибке запуска. Старые `--kind=camera` и `--kind=tester` сохраняют `/api/v1/measurements`; устройства каталога используют `/api/v1/operations`.

## Устройства и результаты

| ID | Модель | Рабочее место | Операция и результат |
|---|---|---|---|
| `paste-printer-01` | NeoDen YS350 | `paste-printing` | `print-paste`: трафарет, процент покрытия пастой |
| `component-placer-01` | NeoDen4 | `component-placement` | `place-components`: программа и число установленных компонентов |
| `reflow-oven-01` | NeoDen IN6 | `reflow-soldering` | `reflow`: профиль и пиковая температура |
| `optical-inspector-01` | NeoDen ND880 | `optical-inspection` | `inspect`: программа и число обнаруженных дефектов |
| `manual-soldering-01` | Weller WT1010M | `manual-assembly` | `solder`: инструкция, температура жала и число соединений |
| `programmer-01` | STLINK-V3SET | `programming-test` | `program`: имя образа прошивки и результат проверки |
| `test-power-supply-01` | Keysight E36312A | `programming-test` | `supply-power`: напряжение и ограничение тока |
| `test-multimeter-01` | Keysight 34461A | `programming-test` | `measure-voltage`: напряжение и прохождение допуска |

Для A/B встроены разные учебные рецепты. Например, монтаж содержит 42/64 компонента, профиль оплавления — 240/245 °C, испытание — 3,3/5 В. Эти числа служат только демонстрации изменения конфигурации: они не являются технологическими рекомендациями. Прошивки, трафареты и программы представлены именами артефактов; реальные файлы не загружаются и не исполняются.

Каждый запрос операции создаёт одно наблюдение. У AOI и мультиметра каждое десятое наблюдение получает `accepted=false`; это воспроизводимый брак изделия, который сам по себе не делает оборудование неготовым. Фоновая генерация включается отдельно, как описано ниже. Движение плат и согласованное испытание одной платы тремя приборами не моделируются. После перезапуска счётчик начинается с нуля.

## Подготовка, калибровка и отказы

Обычный запуск сразу готов к операциям. Для сценария ручной подготовки:

```bash
./bin/equipment-simulator --equipment=manual-soldering-01 --product=board-a --require-setup
```

До подтверждения `/readyz` возвращает 503, а операции — 409. Подтверждение через HTTP является командой сценария симуляции, а не реальным сигналом от станка:

```bash
curl -sS -X POST localhost:8080/api/v1/setup
curl -sS localhost:8080/readyz
```

Управляемые режимы:

| `mode` | Поведение |
|---|---|
| `normal` | Исправность и калибровка восстановлены; ранее сброшенная подготовка всё ещё требует подтверждения. |
| `fault` | Неисправность: readiness 503, операции, подготовка и калибровка недоступны; liveness остаётся 200. |
| `uncalibrated` | Readiness 503 до `POST /api/v1/calibrate`. Калибровка не подтверждает подготовку рабочего места. |
| `unprepared` | Сбрасывает подтверждение подготовки; требуется `POST /api/v1/setup`. |
| `slow` | Операция задерживается на `--latency` (по умолчанию 2 секунды). Изменение состояния во время задержки отменяет результат с кодом 409. |

```bash
curl -sS -X PUT localhost:8080/api/v1/mode -H 'Content-Type: application/json' -d '{"mode":"fault"}'
curl -i localhost:8080/healthz
curl -i localhost:8080/readyz
curl -sS -X PUT localhost:8080/api/v1/mode -H 'Content-Type: application/json' -d '{"mode":"normal"}'
```

Подготовка, режим отказа и состояние калибровки хранятся в памяти. HTTP API не меняет изделие или рецепт: для этого требуется новый запуск с нужными аргументами. `TechProcess.spec.parameters.product` — описательный параметр, симулятор его не читает; фактический продукт выбирает `--product` в шаблоне.

## Периодическая телеметрия без MQTT

Сначала остановите предыдущий процесс, если он использует порт 8080. Из корня репозитория запустите:

```bash
make build-simulator
./bin/equipment-simulator \
  --equipment=reflow-oven-01 --product=board-a --revision=demo-a \
  --listen=127.0.0.1:8080 \
  --telemetry-interval=5s --simulation-seed=42 \
  --telemetry-namespace=factory-demo --telemetry-tech-process=line-one \
  > /tmp/factory-oven-telemetry.jsonl
```

Команда работает до Ctrl+C. В другом терминале просматривайте полный JSON-лог:

```bash
tail -f /tmp/factory-oven-telemetry.jsonl
```

Записи с `msg="Generated telemetry snapshot"` содержат объект `snapshot` по [контракту v1](../architecture/telemetry.md). При наличии `jq` снимки можно выделить отдельно:

```bash
jq -c 'select(.snapshot != null) | .snapshot' /tmp/factory-oven-telemetry.jsonl
```

На этапе 3 доставка реализована как вывод в лог. MQTT и отдельный процесс приёмника добавляются на этапе 4. По умолчанию `--telemetry-interval=0` отключает генерацию. Для включения обязательны положительный интервал, явно переданный `--simulation-seed` (в том числе `0`), namespace и имя процесса. Для legacy `--kind=camera/tester` генерация недоступна. Интервал 5 секунд соответствует сроку свежести приёмника 20 секунд; при его изменении нужно согласовать эти параметры.

Первый снимок формируется сразу, затем — с заданным интервалом. Готовое устройство выполняет одну автоматическую операцию за цикл. Результаты HTTP-операций и автоматических операций используют общие счётчики: каждый десятый завершённый контроль AOI или мультиметра отклоняет изделие. Пропущенные циклы не догоняются; это условный темп стенда, а не производительность реального станка.

Seed записан в каждом снимке. С ним воспроизводятся синтетические длительности и колебания показаний при одинаковом порядке циклов, HTTP-операций и смен состояния. Реальное время, длительность HTTP-запросов и уникальный `source_instance_id` могут различаться между запусками. Для точного сравнения тесты используют управляемые часы. Перезапуск создаёт новый экземпляр источника и сбрасывает счётчики и номер снимка.

Проверка отказа в другом терминале:

```bash
curl -sS -X PUT localhost:8080/api/v1/mode -H 'Content-Type: application/json' -d '{"mode":"fault"}'
curl -i localhost:8080/healthz
curl -i localhost:8080/readyz
```

Во время отказа `/healthz` возвращает 200, `/readyz` — 503. Снимки продолжают поступать с новым `observed_at` и `sequence`, `healthy=false`, без роста завершённых операций. Для печи отсутствует фактическая температура; уставка сохраняется, `temperature_ready=0`. Неготовность сама по себе не увеличивает ошибки, поскольку автоматическая операция не начинается. Явный HTTP-запрос операции, получивший 409, увеличит `operation_errors_total`.

```bash
curl -sS -X PUT localhost:8080/api/v1/mode -H 'Content-Type: application/json' -d '{"mode":"uncalibrated"}'
curl -sS -X POST localhost:8080/api/v1/calibrate
curl -sS -X PUT localhost:8080/api/v1/mode -H 'Content-Type: application/json' -d '{"mode":"unprepared"}'
curl -sS -X POST localhost:8080/api/v1/setup
curl -sS -X PUT localhost:8080/api/v1/mode -H 'Content-Type: application/json' -d '{"mode":"normal"}'
```

В `uncalibrated` и `unprepared` heartbeat также продолжается, а операции ждут восстановления готовности. `slow` с положительным `--latency` начинает операцию на одном цикле и завершает на первом цикле после истечения задержки; новый цикл операции начинается на следующем heartbeat. Готовность при этом сохраняется. Смена режима, подтверждение подготовки или калибровка отменяют незавершённую операцию с увеличением счётчика ошибок. Длительные HTTP-операции используют такую же проверку смены состояния; отменённый HTTP-запрос не создаёт завершённую операцию.

Ошибки функции отправки снимка не меняют готовность и не вызывают повторную отправку старого снимка. Эти случаи проверяются unit-тестами; реальная проверка разрыва MQTT появится вместе с транспортом.

```bash
make test-unit
go test -race ./internal/simulator ./cmd/equipment-simulator
```

## Запуск всего участка

[Локальный runbook](local-development.md) описывает запуск Kind и переход A/B. Примеры создают восемь Deployment с `Recreate`, например `line-one-reflow-oven-01`. Три прибора испытаний — отдельные pod с общим логическим рабочим местом; совместный тестовый сценарий для них ещё не реализован.

Для доступа к одному устройству:

```bash
kubectl -n factory-demo port-forward deployment/line-one-reflow-oven-01 8080:8080
```

После этого доступны те же команды `curl`. Каждый экземпляр симулятора имеет собственные состояние и счётчик.

Обновление всех компонентов пока выполняется существующим оператором без порядка между рабочими местами. Последовательный переход и автоматический rollback остаются следующим этапом. Архитектурные границы зафиксированы в [ADR 0005](../adr/0005-equipment-simulation.md).
