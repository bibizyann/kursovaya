# Телеметрия через MQTT: один симулятор и приёмник

Этап 4 запускается локально без Kubernetes. Нужны Go из `go.mod`, Docker с работающим daemon и `curl`. Mosquitto запускается в контейнере; симулятор и приёмник — отдельными Go-бинарниками на хосте. Prometheus и Grafana появятся на этапе 7; сейчас формат метрик можно проверить через `curl`.

## Сборка и брокер

Все команды выполняются из корня репозитория:

```bash
make build-simulator build-telemetry-receiver
docker pull eclipse-mosquitto:2.0.22
docker run -d --name factory-mqtt-demo \
  -p 127.0.0.1:1883:1883 \
  --mount "type=bind,src=$(pwd)/infra/mqtt/mosquitto.conf,dst=/tmp/mosquitto.conf,readonly" \
  eclipse-mosquitto:2.0.22 mosquitto -c /tmp/mosquitto.conf
```

Имя `factory-mqtt-demo` и порты 1883, 8080, 9091 должны быть свободны. Конфигурация в `infra/mqtt/mosquitto.conf` допускает анонимное подключение для локальной демонстрации. Порт контейнера опубликован только на loopback. Сохранение состояния брокера на диск выключено; размер сообщения ограничен 64 КиБ, пакета — 70 000 байт с учётом MQTT-заголовков и топика.

## Приёмник

В отдельном терминале:

```bash
./bin/telemetry-receiver \
  --listen=127.0.0.1:9091 \
  --mqtt-broker=tcp://127.0.0.1:1883 \
  --expected=factory-demo/line-one/reflow-oven-01
```

Каждый повторный `--expected` добавляет поток `namespace/tech_process/equipment_id`. Например, второе устройство или другой процесс задаётся ещё одним таким аргументом. Пустой список, повторяющиеся потоки и неизвестные ID оборудования отклоняются при запуске. Приёмник подписывается на точные топики из списка, без wildcard-подписки на весь завод.

Пока симулятор не запущен:

```bash
curl -sS localhost:9091/healthz
curl -sS localhost:9091/metrics
```

Ожидаются `{"status":"alive"}` и метрика `factory_equipment_telemetry_fresh` со значением `0`. Физических показаний и признака исправности пока нет. Приёмник поднимает HTTP даже при недоступном брокере и повторяет подключение в фоне.

## Симулятор

В ещё одном терминале:

```bash
./bin/equipment-simulator \
  --listen=127.0.0.1:8080 \
  --equipment=reflow-oven-01 --product=board-a --revision=demo-a \
  --telemetry-interval=5s --simulation-seed=42 \
  --telemetry-namespace=factory-demo --telemetry-tech-process=line-one \
  --mqtt-broker=tcp://127.0.0.1:1883
```

Снимки продолжают выводиться в JSON-лог и предлагаются MQTT-отправителю. Первый снимок может быть отброшен, пока соединение ещё устанавливается. На следующем цикле отправится новый.

Топик этого устройства:

```text
factory/v1/factory-demo/line-one/reflow-oven-01/telemetry
```

Проверьте:

```bash
curl -sS localhost:8080/api/v1/status
curl -sS localhost:9091/metrics
```

В метриках появятся свежесть `1`, исправность `1`, температура около 240 °C, уставка и накопительный счётчик операций. Метки `namespace`, `tech_process`, `workstation`, `equipment_id` определяют устройство; `factory_equipment_info` дополнительно содержит изделие, рецепт и ревизию.

## Неисправность и потеря связи

Сначала имитируйте неисправность:

```bash
curl -sS -X PUT localhost:8080/api/v1/mode \
  -H 'Content-Type: application/json' -d '{"mode":"fault"}'
curl -i localhost:8080/readyz
curl -sS localhost:9091/metrics
```

После следующего снимка свежесть останется `1`, исправность станет `0`, фактическая температура исчезнет, завершённые операции перестанут добавляться. `/readyz` вернёт 503, `/healthz` симулятора останется 200.

Восстановите готовность и отключите брокер:

```bash
curl -sS -X PUT localhost:8080/api/v1/mode \
  -H 'Content-Type: application/json' -d '{"mode":"normal"}'
docker stop factory-mqtt-demo
curl -i localhost:8080/readyz
curl -sS localhost:8080/api/v1/status
curl -sS localhost:9091/metrics
```

Симулятор останется готовым и продолжит автоматические операции. Через 20 секунд от времени последнего принятого наблюдения приёмник выдаст свежесть `0`; исправность, температура, счётчики и информация о ревизии исчезнут из текущего экспорта. Сохранятся свежесть и timestamp последнего принятого наблюдения. Приёмник не считает отсутствие связи доказательством поломки станка.

```bash
docker start factory-mqtt-demo
curl -sS localhost:9091/metrics
```

После переподключения и следующего цикла симулятора свежесть вернётся к `1`. Приёмник увидит актуальное накопленное число операций. Промежуточные снимки не воспроизводятся; времена операций внутри разрыва восстановить нельзя.

## Перезапуски и retained

Каждая публикация использует QoS 1 и `retain=true`. Брокер хранит последний снимок на топик в памяти и передаёт его новой подписке. Это позволяет перезапущенному приёмнику сразу восстановить текущее состояние, если снимок ещё свежий. Остановите приёмник через Ctrl+C и запустите той же командой, чтобы проверить это.

Если остановить симулятор и подождать дольше срока свежести, retained-снимок не сделает устройство готовым в мониторинге: приёмник проверяет исходный `observed_at`, а не время доставки. Перезапуск самого брокера в этом стенде удаляет retained-снимки, поскольку `persistence=false`.

После перезапуска симулятора меняются `source_instance_id` и время запуска, а счётчики начинаются заново. Новый источник с более поздним временем запуска заменяет предыдущий. Для демонстрации новой конфигурации остановите прежний симулятор и измените `--product=board-b --revision=demo-b`: уставка печи станет 245 °C. Для одного потока должен работать один активный источник.

## Ограничения доставки и параметры

Отправка не блокирует цикл симуляции: в отдельном worker находится не более одной отправки в полёте и одного ожидающего снимка. Новый ожидающий снимок заменяет предыдущий. При отключении ожидающий снимок сбрасывается; новые снимки до подключения отбрасываются. Все соединения используют clean session и новый клиент с памятью без истории. Встроенное автоматическое переподключение Paho выключено, чтобы библиотека не возобновляла старые публикации.

QoS 1 допускает повторы. Приёмник проверяет идентификатор запуска и номер снимка, поэтому повторная доставка не увеличивает счётчики. Подтверждение брокером не доказывает, что приёмник принял сообщение: некорректный JSON, несовпадение топика и содержимого или устаревшие данные отклоняются с записью причины в лог.

| Параметр | Значение по умолчанию | Где используется |
|---|---|---|
| `--mqtt-broker` | Пусто у симулятора; `tcp://127.0.0.1:1883` у приёмника | Оба процесса |
| `--mqtt-timeout` | `3s` | Оба процесса; сетевые операции и ожидание подтверждения |
| `--mqtt-retry-interval` | `1s` | Оба процесса; пауза перед новым соединением |
| `--freshness-timeout` | `20s` | Приёмник |
| `--max-future-skew` | `5s` | Приёмник |

Без `--mqtt-broker` симулятор сохраняет режим JSON-лога. С MQTT обязательно включить генерацию с явным seed. Доступны `tcp://host:port` и `ssl://host:port`; TLS проверяет сертификат через системные доверенные центры. Имя пользователя и пароль при необходимости задаются переменными `FACTORY_MQTT_USERNAME` и `FACTORY_MQTT_PASSWORD`. Настройка заводских ACL и сертификатов относится к развёртыванию конкретной инфраструктуры; локальный пример использует loopback и анонимный доступ.

Семантика клиента описана в [Eclipse Paho](https://github.com/eclipse-paho/paho.mqtt.golang/tree/v1.5.1), параметры брокера — в [документации Mosquitto](https://mosquitto.org/man/mosquitto-conf-5.html).

## Проверки и завершение

```bash
make test-unit
make test-mqtt
```

`make test-mqtt` запускает тесты с `-race`, создаёт отдельный контейнер с уникальным именем и свободным портом, проверяет retained-доставку, повторы, истечение свежести, перезапуск брокера и приёмника, затем удаляет только свой контейнер. Нужен Docker и образ `eclipse-mosquitto:2.0.22`; образ можно явно переопределить через `MQTT_BROKER_IMAGE`. Обычные unit-тесты не требуют брокера.

Завершите оба бинарника через Ctrl+C и удалите демонстрационный брокер:

```bash
docker rm -f factory-mqtt-demo
```
