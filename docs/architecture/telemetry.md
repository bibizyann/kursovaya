# Телеметрия оборудования: контракт и приёмник

Этот документ задаёт входной контракт мониторинга согласно [ADR 0006](../adr/0006-simulated-telemetry.md). Программа оборудования считается внешним источником готовых наблюдений. В стенде её заменяет симулятор. Реализованы контракт снимков, генератор симуляторов, MQTT-транспорт, приёмник в памяти и отдельный процесс с Prometheus collector. Локальная связка запускается по [MQTT-runbook](../runbooks/telemetry-mqtt.md). Метрики оператора и проверка готовности целевой ревизии также реализованы. Для восьми устройств добавлен [Kind-профиль](../runbooks/telemetry-kind.md) с отдельными Mosquitto и receiver; локальный E2E ожидает устранения ограничения inotify. Развёртывание Prometheus и графики относятся к этапу 7.

## Граница реализации

```text
В теории: прибор -> программа рабочего места -> готовый снимок
На стенде: симулятор -------------------------> готовый снимок
                                                      |
                                                      v
                    MQTT -> Mosquitto -> Go receiver -> Prometheus -> Grafana
```

Возможные реальные источники описаны в [модели цеха](assembly-workshop.md#реальные-интерфейсы-и-ограничения): SCPI для измерительных приборов, результаты программы прошивки, отчёты AOI или ввод оператора. Наличие нужного интерфейса у конкретного станка требует проверки при реальном внедрении. Драйверы и способы чтения оборудования в дипломе не реализуются.

## Снимок версии 1

Тип `Snapshot` находится в [internal/telemetry](../../internal/telemetry/snapshot.go). Один JSON-объект содержит полный актуальный снимок одного устройства; максимальный размер — 64 КиБ. Для входящих байтов используется `telemetry.Decode`, для уже построенного Go-значения — `Snapshot.Validate`.

| Поле | Смысл |
|---|---|
| `schema_version` | Ровно `1` |
| `namespace`, `tech_process` | Область наблюдения; соответственно DNS label до 63 символов и DNS subdomain до 253 символов |
| `equipment_id`, `workstation` | Стабильное устройство и логическое рабочее место из Go-каталога; не имя узла или pod |
| `source_instance_id` | Новый уникальный токен при каждом запуске источника, до 128 ASCII-символов: буквы, цифры, `.`, `_`, `-`; начинается с буквы или цифры |
| `source_started_at` | Время запуска этого экземпляра |
| `sequence` | Положительный номер снимка в пределах экземпляра, начинается с 1 |
| `observed_at` | Время формирования снимка, не раньше запуска источника |
| `product`, `recipe_id`, `revision` | Наблюдаемое изделие, применённый рецепт и ревизия; непустые строки без пробельных и управляющих символов, до 128/256/128 байт |
| `simulation_seed` | Необязательный `int64`; значение `0` отличается от отсутствия поля |
| `state` | Три обязательных boolean: `healthy`, `calibrated`, `setup_complete` |
| `readings` | Необязательный словарь доступных числовых показаний с фиксированными именами и единицами |
| `counters` | Три обязательных неотрицательных целочисленных счётчика `uint64`, включая явные нули |

Имена полей JSON используют `snake_case`. Неизвестные поля, неподдерживаемая версия, пропущенные обязательные поля и обязательные поля со значением `null` отклоняются. Существующие HTTP-ответы симуляторов с `camelCase` остаются отдельным API и не меняются.

Времена передаются в RFC3339; рекомендуется UTC. Декодер также принимает явное смещение часового пояса. `observed_at` фиксируется заново при формировании снимка, даже если оборудование не меняло состояния. Поле `UpdatedAt` существующего HTTP-статуса для heartbeat не подходит.

Согласованная область потока — `(namespace, tech_process, equipment_id)`. MQTT использует топик `factory/v1/{namespace}/{tech_process}/{equipment_id}/telemetry`. Приёмник проверяет точное совпадение области топика с сообщением и принимает только заранее заданные потоки.

## Счётчики и состояние

| Счётчик | Значение |
|---|---|
| `operations_total` | Все успешно завершённые операции, в том числе проверки, отклонившие изделие |
| `operation_errors_total` | Попытки, которые не удалось завершить из-за ошибки; не входят в `operations_total` |
| `rejected_operations_total` | Завершённые проверки, отклонившие изделие; подмножество `operations_total`, используется для AOI и мультиметра |

Это накопленные значения, а не приращения. Приёмник заменяет снимок целиком и не прибавляет счётчики при каждом получении. Один снимок может содержать результаты нескольких операций. Номер снимка не равен счётчику операций и не заменяет `Sequence` существующего HTTP API.

Отклонённая плата не означает неисправность оборудования. Признаки исправности, калибровки и подготовки независимы; при неисправности heartbeat продолжает описывать состояние, а число успешно выполненных операций не растёт. Состояние `unknown` формирует приёмник при отсутствии свежего снимка.

`product`, `recipe_id` и `revision` не сверяются с числами встроенного учебного рецепта: контракт передаёт наблюдаемую конфигурацию, а не доказывает её соответствие желаемой. Проверка целевой ревизии выполняется оператором по состоянию Kubernetes workloads, как описано ниже.

## Показания и единицы

Для каждого из восьми устройств допустимо `last_operation_duration_seconds` — длительность последней завершённой операции в секундах. До первой операции это показание опускается. Остальные допустимые поля:

| Устройство | Дополнительные поля `readings` | Единицы |
|---|---|---|
| `paste-printer-01` | Нет; состояние, счётчики и длительность | — |
| `component-placer-01` | Нет; состояние, счётчики и длительность | — |
| `reflow-oven-01` | `temperature_celsius`, `target_temperature_celsius`, `temperature_ready` | °C, °C, 0/1 |
| `optical-inspector-01` | Нет; результат отражают счётчики проверок | — |
| `manual-soldering-01` | Нет; состояние, счётчики и длительность | — |
| `programmer-01` | Нет; успехи и ошибки отражают счётчики | — |
| `test-power-supply-01` | `voltage_volts`, `target_voltage_volts`, `current_amperes`, `current_limit_amperes`, `output_enabled` | В, В, А, А, 0/1 |
| `test-multimeter-01` | `voltage_volts`, `min_voltage_volts`, `max_voltage_volts` | В |

Реестр доступен через `ReadingDefinitions`. Произвольные имена метрик не принимаются. Все значения конечны: `NaN` и бесконечности запрещены. Длительность неотрицательна, температура не ниже абсолютного нуля, boolean-показания равны строго 0 или 1. Напряжение и ток могут быть знаковыми; производственные допуски не являются ограничениями формата. Границы напряжения либо обе отсутствуют, либо образуют упорядоченную пару.

Отсутствующее показание означает «недоступно», а не ноль. Пустой, отсутствующий или `null` словарь `readings` означает отсутствие всех измерений; `null` вместо отдельного числового значения запрещён. Новый снимок не наследует показания предыдущего. Уставки никогда не подменяют фактические значения.

## Генерация в симуляторах

[Генератор](../../internal/simulator/generator.go) включается явно через `simulator.Config.Telemetry`. Конфигурация требует интервал, namespace, имя процесса и seed. CLI и пример наблюдения за JSON-снимками описаны в [runbook](../runbooks/equipment-simulation.md#периодическая-телеметрия-без-mqtt).

`Server.Generate()` выполняет один цикл без ожиданий и возвращает снимок. `RunGenerator(ctx, emit)` выполняет первый цикл сразу и последующие по таймеру. Функция `emit` вызывается вне блокировки состояния; она должна своевременно возвращать управление и учитывать отмену контекста. Ошибка функции отправки записывается в лог, готовность не меняется. Сам генератор не повторяет доставку. CLI записывает снимки в JSON-лог; при заданном `--mqtt-broker` также передаёт их отдельному MQTT-worker через ограниченный буфер.

Все счётчики и признаки готовности обновляются под одной блокировкой с HTTP API. Обычный готовый цикл завершает одну синтетическую операцию; неготовый только формирует heartbeat. Накопленные операции включают и HTTP-запросы. Номер снимка растёт независимо от HTTP `sequence`, который считает завершённые операции. Источник получает уникальный ID при запуске, даже при повторном использовании seed.

| Данные | Модель генерации |
|---|---|
| Длительность | Для обычной автоматической операции — случайные 5–20% интервала; для `slow` — заданная задержка; для HTTP — прошедшее время выполнения |
| Печь | Учебная уставка рецепта, синтетическая температура в пределах ±0,5 °C, признак готовности из общего состояния |
| Источник питания | Уставки рецепта, синтетическое напряжение ±0,5% и ток 30–40% ограничения; выход включён только при готовности |
| Мультиметр | Напряжение последней завершённой операции и допуски рецепта; каждая десятая проверка вне допуска |
| Остальные устройства | Готовность, длительность, счётчики и конфигурация; случайные физические показания не добавляются |

У неготовых устройств фактические температура, напряжение и ток отсутствуют. Уставки, допуски и длительность последней завершённой операции остаются доступными. Брак изделия учитывается отдельно от ошибки операции. Отклонённые HTTP-попытки и прерванные операции увеличивают ошибки, а ожидание готовности между автоматическими циклами — нет.

Генератор не моделирует физическую динамику, движение плат и связь трёх испытательных приборов. Воспроизводимость требует одинаковых seed, шагов времени и порядка воздействий. `Config.Now` позволяет проверять это без ожиданий. Уход часов назад останавливает текущий runner с диагностикой, не меняя readiness; нужен разбор причины и перезапуск генератора после восстановления времени.

## Порядок и свежесть на стороне приёмника

Эти правила реализованы в [internal/telemetryreceiver](../../internal/telemetryreceiver/receiver.go). Пакет контракта `internal/telemetry` сохраняет только проверки отдельного снимка без хранения состояния и чтения часов.

1. Для одного экземпляра принимаются только возрастающие `sequence` и неубывающее `observed_at`. Повторный или меньший номер игнорируется и не обновляет свежесть.
2. В течение экземпляра неизменны время запуска, изделие, рецепт, ревизия и `simulation_seed`. Накопительные счётчики не уменьшаются. Смена этой конфигурации или сброс счётчиков требует нового экземпляра.
3. Новый `source_instance_id` заменяет текущий только с большим `source_started_at`. Более старый запуск не может вернуть старую ревизию. Равное время разных экземпляров — конфликт; сообщения отклоняются с диагностикой. В стенде предполагается один активный издатель на устройство и синхронизированные часы.
4. Стартовые параметры приёмника: срок свежести 20 секунд и допустимое опережение часов источника 5 секунд. Возраст ровно 20 секунд уже считается устаревшим; опережение ровно 5 секунд допустимо. Это настраиваемые параметры стенда. Проверяются времена наблюдения, а не только получения; retained-сообщение само по себе не считается свежим.
5. Ожидаемые, но ещё не приславшие данные устройства видны как `unknown`. После истечения срока свежести физические показания не экспортируются как актуальные. Недоступность MQTT не меняет readiness симулятора.
6. После перезапуска приёмник теряет состояние и восстанавливает его по новым допустимым свежим снимкам. Гарантии обнаружения всех повторов через перезапуск или восстановления пропущенной истории нет.

QoS 1 требует обработки повторов, но не обещает сохранения каждой производственной операции. Восстановление накопительных счётчиков после разрыва не восстанавливает времена отдельных операций. Графики через такие разрывы не должны изображать точную производительность по исходному времени.

## Использование приёмника

`telemetryreceiver.New(Config)` получает непустой список `Expected`: ключи `(namespace, tech_process, equipment_id)` из известного каталога. Неожиданные потоки отклоняются. Ожидаемый список фиксирован на время жизни приёмника; память ограничена одним последним принятым снимком на поток. Даже после истечения свежести этот снимок хранится для проверки порядка сообщений. История не накапливается.

Методы приёмника:

- `Accept(snapshot)` проверяет контракт, порядок и время наблюдения, копирует снимок и заменяет предыдущий целиком. Возвращает `(true, nil)` при принятии, `(false, nil)` при игнорировании старого номера или старого экземпляра и `(false, error)` при некорректных данных. Отклонённое сообщение не меняет состояние. Входящий JSON сначала нужно декодировать через `telemetry.Decode`, чтобы проверить наличие обязательных полей.
- `Observations()` возвращает отдельные копии наблюдений в порядке ожидаемого списка с вычисленной на момент чтения свежестью. Вызывающий код не может изменить хранимые снимки через эти копии.
- `Collector()` создаёт Prometheus collector для регистрации в реестре вызывающего приложения.
- `MetricsHandler()` создаёт HTTP-обработчик с отдельным Prometheus registry. Его можно подключить через `mux.Handle("GET /metrics", receiver.MetricsHandler())`.

Приём и чтение потокобезопасны. Переданный в `Accept` снимок нельзя одновременно изменять из другой goroutine. Для тестов часы подставляются через `Config.Now`; `FreshnessTimeout` и `MaxFutureSkew` задают временные пределы, нулевые значения выбирают значения по умолчанию.

Библиотеку запускает отдельный процесс `cmd/telemetry-receiver`: он принимает список потоков через повторяемый `--expected`, поднимает `/metrics` и `/healthz`, а MQTT-подписки поддерживает в фоне. У приёмника нет Kubernetes-клиента, доступа к CR или влияния на readiness.

## MQTT-транспорт

Пакет `internal/telemetrymqtt` использует MQTT 3.1.1 и Eclipse Paho v1.5.1. Публикации и подписки используют QoS 1. Публикация содержит полный JSON-снимок и `retain=true`; Mosquitto хранит последнее сообщение на топик. Retained не отменяет проверок времени и порядка в приёмнике.

`Publisher.Publish(ctx, snapshot)` проверяет и кодирует снимок, затем без сетевого ожидания предлагает его worker. Возвращаемый `nil` означает принятие в буфер, а не подтверждение от брокера. Один publisher обслуживает один поток; не более одного снимка ожидает отправки и одного находится в полёте. Новый ожидающий снимок заменяет прежний. При отключении буфер сбрасывается, новые снимки отбрасываются до восстановления соединения.

`Publisher.Run` и `Subscriber.Run` управляют подключениями отдельно от генератора и HTTP-сервера. Каждый сеанс создаёт новый Paho-клиент с пустым хранилищем в памяти, `clean_session=true` и выключенным встроенным reconnect. После ошибки публикации или таймаута сеанс закрывается; после паузы создаётся новый. Это исключает автоматическое возобновление истории публикаций библиотекой. Уже отправленный пакет мог успеть дойти до брокера до разрыва — проверки повторов всё равно обязательны.

`Subscriber` подписывается на точные топики ожидаемого списка при каждом подключении. Обработчик декодирует ограниченный по размеру JSON, сверяет топик с областью снимка и вызывает `Receiver.Accept`. MQTT не меняет рецепт, CR или готовность симулятора. `/healthz` приёмника отражает работу процесса, а отсутствие свежих данных видно в метриках.

Сетевые операции и ожидание подтверждений ограничены таймаутами, сокет закрывается при отмене. Начальная недоступность брокера не препятствует запуску обоих HTTP API. Текущий локальный Mosquitto не сохраняет данные на диск; после его перезапуска поступают новые снимки. Пошаговая проверка отказов и параметры CLI приведены в [runbook](../runbooks/telemetry-mqtt.md).

## Экспорт в Prometheus

Все серии имеют метки `namespace`, `tech_process`, `workstation`, `equipment_id`. Только `factory_equipment_info` дополнительно содержит `product`, `recipe_id`, `revision`. `sequence`, `source_instance_id`, timestamps и seed не становятся метками.

| Метрика | Тип | Когда экспортируется и что означает |
|---|---|---|
| `factory_equipment_telemetry_fresh` | gauge | Всегда для ожидаемого устройства: 1 при свежем снимке, иначе 0 |
| `factory_equipment_last_observation_timestamp_seconds` | gauge | После первого принятого снимка, включая период устаревания; Unix timestamp времени его формирования |
| `factory_equipment_healthy` | gauge | Только свежий снимок: исправность, 0/1 |
| `factory_equipment_calibrated` | gauge | Только свежий снимок: результат имитируемой калибровки, 0/1 |
| `factory_equipment_setup_complete` | gauge | Только свежий снимок: завершённость подготовки, 0/1 |
| `factory_equipment_info` | gauge | Только свежий снимок: значение 1 с метками применённой конфигурации |
| `factory_operations_total` | counter | Только свежий снимок: накопленные завершённые операции |
| `factory_operation_errors_total` | counter | Только свежий снимок: накопленные неудачные попытки |
| `factory_rejected_operations_total` | counter | Только свежий снимок: накопленные отклонённые изделия |
| `factory_<имя показания>` | gauge | Только присутствующее показание свежего снимка; например, `factory_temperature_celsius`, `factory_voltage_volts`, `factory_last_operation_duration_seconds` |

Названия и единицы показаний перечислены выше. Счётчики передаются как абсолютные значения: повторная доставка или scrape не увеличивает их. Новый экземпляр источника может начать счётчики с нуля. При смене ревизии collector выдаёт только текущую информационную серию; история прошлых ревизий может оставаться в Prometheus.

Свежая неисправность — это `telemetry_fresh=1` и `healthy=0`. Отсутствие данных — `telemetry_fresh=0` без метрики `healthy`, физических показаний, счётчиков и `info`. Ещё не приславшее допустимых данных устройство не имеет и timestamp. Графики должны учитывать свежесть, чтобы отличать неизвестное состояние от неисправности или нулевого показания; сама Grafana добавляется на этапе 7.

## Метрики оператора и готовность ревизии

У оператора собственный `/metrics`, отдельный от `telemetry-receiver`. [Collector техпроцессов](../../internal/controller/metrics.go) зарегистрирован в существующем metrics registry manager. Он читает CR из кэша controller-runtime и формирует значения из сохранённого status; MQTT в этой цепочке не участвует. Стандартные метрики Reconcile остаются доступными на том же endpoint.

| Метрика | Смысл |
|---|---|
| `factory_techprocess_status_current` | 1, если status наблюдал текущую generation процесса и UID/generation шаблона; иначе 0 |
| `factory_techprocess_condition` | По три серии `status=true/false/unknown` для каждой `condition=Ready/Progressing/Degraded`; ровно одна активна |
| `factory_techprocess_desired_workloads` | Желаемое число экземпляров workloads в актуальном status |
| `factory_techprocess_ready_workloads` | Число экземпляров, готовность которых подтверждена для целевой ревизии |
| `factory_techprocess_revision_info` | Значение 1 с меткой текущей согласованной `revision` |
| `factory_techprocess_rollout_started_timestamp_seconds` | Сохранённое время начала текущего rollout |
| `factory_techprocess_rollout_completed_timestamp_seconds` | Сохранённое время первой готовности текущей ревизии |
| `factory_techprocess_rollout_duration_seconds` | `completedAt - startedAt` в секундах; отсутствует до завершения rollout |

Это gauges с общими метками `namespace` и `tech_process`. Только Conditions имеют метки `condition`, `status`, а информационная серия — `revision`. Причины ошибок, UID, поколения и временные значения не становятся метками. Удаление CR удаляет его серии на следующем scrape. Ошибка чтения кэша приводит к ошибке сбора метрик, а не к ложным нулевым значениям.

При устаревшем status Conditions представлены как `unknown`, а метрики ревизии, количества workloads и времени не экспортируются. Отсутствующая Condition также означает `unknown`. Обработанная ошибка отсутствия шаблона, напротив, даёт актуальный `Degraded=true`; показатели rollout для неё не выводятся. Количества workloads отсутствуют, пока контроллер ещё не собрал статусы компонентов.

При смене ревизии контроллер сохраняет `startedAt` до изменения дочерних ресурсов и сбрасывает `completedAt`. Первое достижение Ready фиксирует `completedAt`. Повторный Reconcile, новый scrape и перезапуск оператора не меняют эти границы. Последующая потеря готовности на той же ревизии меняет Conditions, но сохраняет время первого rollout и не превращается в его таймаут. Новый rollout начинается при новом хеше желаемой конфигурации.

Длительность отражает наблюдение готовности контроллером с точностью сериализованных timestamp, а не физическую длительность переналадки станка. История хранится только в будущих выборках Prometheus: gauge не гарантирует фиксацию каждого краткого rollout между опросами. При некорректном обратном порядке времён длительность не экспортируется.

Проверка Ready использует ревизию на workload и pod template, `observedGeneration`, число обновлённых экземпляров и их доступность. Для Deployment также должны исчезнуть старые и известные завершающиеся реплики; для DaemonSet не должно быть размещений вне требуемых узлов. При смешанных ревизиях aggregate Kubernetes status не позволяет точно выделить готовые новые экземпляры, поэтому `readyWorkloads` для такого компонента консервативно равен нулю. Пустой DaemonSet без подходящих узлов не готов.

Условия готовности согласованы с [критериями завершения Deployment в Kubernetes](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/#complete-deployment). Исправность, подготовка и калибровка симулятора по-прежнему проверяются его `/readyz`; оператор использует результат Kubernetes readiness probes. Реальный аппаратный статус из MQTT не подменяет этот механизм.

В `TechProcess.status` добавлены `observedTemplateGeneration` и `observedTemplateUID`, поскольку изменение шаблона не меняет generation самого процесса. Перед записью status контроллер сверяет исходные поколения и UID с повторно прочитанными объектами; patch использует optimistic locking. Если desired state успел измениться, старый результат не записывается как наблюдение новой generation. Изменения двух разных CR не являются атомарными: метрики дополнительно сверяют сохранённую версию шаблона с текущей.

## Примеры и проверка

В [internal/telemetry/testdata](../../internal/telemetry/testdata/) находятся восемь полных JSON-снимков, по одному на каждый идентификатор оборудования. Они проходят декодирование, проверку каталога и обратное кодирование в unit-тестах. Пример печи: [reflow-oven-01.json](../../internal/telemetry/testdata/reflow-oven-01.json).

```bash
go test ./internal/telemetry ./internal/telemetryreceiver
go test -race ./internal/telemetryreceiver ./internal/simulator ./cmd/equipment-simulator
make test-unit
make test-mqtt  # Docker and an isolated Mosquitto container
```

Метрики оператора проверяются в `internal/controller/metrics_test.go`: повторные scrape и пересоздание collector, изменения процесса и шаблона, удаление CR, неизвестные Conditions и ошибки чтения. Тесты контроллера проверяют обновление ревизии, сохранение времени первого Ready и конфликты status; `internal/workload/readiness_test.go` покрывает смешанные ревизии и задержки доступности Deployment/DaemonSet. Для них выполняются `make test` и `go test -race ./internal/controller ./internal/workload`.

Тесты приёмника проверяют повторы, нарушение порядка, смену экземпляра, конфликты конфигурации, сброс счётчиков, временные границы и одновременный приём со scrape. Проверки используют управляемые часы без ожиданий.

Эти примеры описывают синтетические данные. Они не подтверждают реальную производительность устройств, физический температурный профиль или качество выпускаемых изделий.
