# Контракт телеметрии оборудования

Этот документ задаёт входной контракт мониторинга согласно [ADR 0006](../adr/0006-simulated-telemetry.md). Программа оборудования считается внешним источником готовых наблюдений. В стенде её заменяет симулятор. Реализованы типы, декодирование, валидация и JSON-примеры; приёмник, генератор, MQTT и графики относятся к следующим этапам.

## Граница реализации

```text
В теории: прибор -> программа рабочего места -> готовый снимок
На стенде: симулятор -------------------------> готовый снимок
                                                      |
                                                      v
                    MQTT -> Mosquitto -> Go receiver -> Prometheus -> Grafana
```

Возможные реальные источники описаны в [модели цеха](assembly-workshop.md#реальные-интерфейсы-и-ограничения): SCPI для измерительных приборов, результаты программы прошивки, отчёты AOI или ввод оператора. Наличие нужного интерфейса у конкретного станка требует проверки при реальном внедрении. Драйверы и способы чтения оборудования в дипломе не реализуются.

## Снимок версии 1

Тип `Snapshot` находится в [internal/telemetry](../../internal/telemetry/snapshot.go). Один JSON-объект содержит полный актуальный снимок одного устройства; максимальный размер — 64 КиБ. Для входящих байтов используется `telemetry.Decode`, для уже построенного Go-значения — `Snapshot.Validate`.

| Поле | Смысл |
|---|---|
| `schema_version` | Ровно `1` |
| `namespace`, `tech_process` | Область наблюдения; соответственно DNS label до 63 символов и DNS subdomain до 253 символов |
| `equipment_id`, `workstation` | Стабильное устройство и логическое рабочее место из Go-каталога; не имя узла или pod |
| `source_instance_id` | Новый уникальный токен при каждом запуске источника, до 128 ASCII-символов: буквы, цифры, `.`, `_`, `-`; начинается с буквы или цифры |
| `source_started_at` | Время запуска этого экземпляра |
| `sequence` | Положительный номер снимка в пределах экземпляра, начинается с 1 |
| `observed_at` | Время формирования снимка, не раньше запуска источника |
| `product`, `recipe_id`, `revision` | Наблюдаемое изделие, применённый рецепт и ревизия; непустые строки без пробельных и управляющих символов, до 128/256/128 байт |
| `simulation_seed` | Необязательный `int64`; значение `0` отличается от отсутствия поля |
| `state` | Три обязательных boolean: `healthy`, `calibrated`, `setup_complete` |
| `readings` | Необязательный словарь доступных числовых показаний с фиксированными именами и единицами |
| `counters` | Три обязательных неотрицательных целочисленных счётчика `uint64`, включая явные нули |

Имена полей JSON используют `snake_case`. Неизвестные поля, неподдерживаемая версия, пропущенные обязательные поля и обязательные поля со значением `null` отклоняются. Существующие HTTP-ответы симуляторов с `camelCase` остаются отдельным API и не меняются.

Времена передаются в RFC3339; рекомендуется UTC. Декодер также принимает явное смещение часового пояса. `observed_at` фиксируется заново при формировании снимка, даже если оборудование не меняло состояния. Поле `UpdatedAt` существующего HTTP-статуса для heartbeat не подходит.

Согласованная область потока — `(namespace, tech_process, equipment_id)`. Для MQTT планируется топик `factory/v1/{namespace}/{tech_process}/{equipment_id}/telemetry`; приёмник должен проверить совпадение области топика с сообщением. MQTT и работа с топиками пока не реализованы.

## Счётчики и состояние

| Счётчик | Значение |
|---|---|
| `operations_total` | Все успешно завершённые операции, в том числе проверки, отклонившие изделие |
| `operation_errors_total` | Попытки, которые не удалось завершить из-за ошибки; не входят в `operations_total` |
| `rejected_operations_total` | Завершённые проверки, отклонившие изделие; подмножество `operations_total`, используется для AOI и мультиметра |

Это накопленные значения, а не приращения. Приёмник заменяет снимок целиком и не прибавляет счётчики при каждом получении. Один снимок может содержать результаты нескольких операций. Номер снимка не равен счётчику операций и не заменяет `Sequence` существующего HTTP API.

Отклонённая плата не означает неисправность оборудования. Признаки исправности, калибровки и подготовки независимы; при неисправности heartbeat продолжает описывать состояние, а число успешно выполненных операций не растёт. Состояние `unknown` формирует приёмник при отсутствии свежего снимка.

`product`, `recipe_id` и `revision` не сверяются с числами встроенного учебного рецепта: контракт передаёт наблюдаемую конфигурацию, а не доказывает её соответствие желаемой. Проверка целевой ревизии относится к оператору и последующим этапам интеграции.

## Показания и единицы

Для каждого из восьми устройств допустимо `last_operation_duration_seconds` — длительность последней завершённой операции в секундах. До первой операции это показание опускается. Остальные допустимые поля:

| Устройство | Дополнительные поля `readings` | Единицы |
|---|---|---|
| `paste-printer-01` | Нет; состояние, счётчики и длительность | — |
| `component-placer-01` | Нет; состояние, счётчики и длительность | — |
| `reflow-oven-01` | `temperature_celsius`, `target_temperature_celsius`, `temperature_ready` | °C, °C, 0/1 |
| `optical-inspector-01` | Нет; результат отражают счётчики проверок | — |
| `manual-soldering-01` | Нет; состояние, счётчики и длительность | — |
| `programmer-01` | Нет; успехи и ошибки отражают счётчики | — |
| `test-power-supply-01` | `voltage_volts`, `target_voltage_volts`, `current_amperes`, `current_limit_amperes`, `output_enabled` | В, В, А, А, 0/1 |
| `test-multimeter-01` | `voltage_volts`, `min_voltage_volts`, `max_voltage_volts` | В |

Реестр доступен через `ReadingDefinitions`. Произвольные имена метрик не принимаются. Все значения конечны: `NaN` и бесконечности запрещены. Длительность неотрицательна, температура не ниже абсолютного нуля, boolean-показания равны строго 0 или 1. Напряжение и ток могут быть знаковыми; производственные допуски не являются ограничениями формата. Границы напряжения либо обе отсутствуют, либо образуют упорядоченную пару.

Отсутствующее показание означает «недоступно», а не ноль. Пустой, отсутствующий или `null` словарь `readings` означает отсутствие всех измерений; `null` вместо отдельного числового значения запрещён. Новый снимок не наследует показания предыдущего. Уставки никогда не подменяют фактические значения.

## Порядок и свежесть на стороне будущего приёмника

Следующие правила фиксируют контракт этапа 2; текущий пакет не хранит состояние и не читает системные часы.

1. Для одного экземпляра принимаются только возрастающие `sequence` и неубывающее `observed_at`. Повторный или меньший номер игнорируется и не обновляет свежесть.
2. В течение экземпляра неизменны время запуска, изделие, рецепт, ревизия и `simulation_seed`. Накопительные счётчики не уменьшаются. Смена этой конфигурации или сброс счётчиков требует нового экземпляра.
3. Новый `source_instance_id` заменяет текущий только с большим `source_started_at`. Более старый запуск не может вернуть старую ревизию. Равное время разных экземпляров — конфликт; сообщения отклоняются с диагностикой. В стенде предполагается один активный издатель на устройство и синхронизированные часы.
4. Стартовые параметры приёмника: срок свежести 20 секунд и допустимое опережение часов источника 5 секунд. Это настраиваемые параметры стенда. Проверяются времена наблюдения, а не только получения; retained-сообщение само по себе не считается свежим.
5. Ожидаемые, но ещё не приславшие данные устройства видны как `unknown`. После истечения срока свежести физические показания не экспортируются как актуальные. Недоступность MQTT не меняет readiness симулятора.
6. После перезапуска приёмник теряет состояние и восстанавливает его по новым допустимым свежим снимкам. Гарантии обнаружения всех повторов через перезапуск или восстановления пропущенной истории нет.

QoS 1 требует обработки повторов, но не обещает сохранения каждой производственной операции. Восстановление накопительных счётчиков после разрыва не восстанавливает времена отдельных операций. Графики через такие разрывы не должны изображать точную производительность по исходному времени.

В Prometheus планируются метки namespace, процесса, рабочего места и устройства. Ревизия отображается отдельной информационной метрикой. `sequence`, `source_instance_id`, timestamps и seed не становятся метками каждой серии.

## Примеры и проверка

В [internal/telemetry/testdata](../../internal/telemetry/testdata/) находятся восемь полных JSON-снимков, по одному на каждый идентификатор оборудования. Они проходят декодирование, проверку каталога и обратное кодирование в unit-тестах. Пример печи: [reflow-oven-01.json](../../internal/telemetry/testdata/reflow-oven-01.json).

```bash
go test ./internal/telemetry
make test-unit
```

Эти примеры описывают синтетические данные. Они не подтверждают реальную производительность устройств, физический температурный профиль или качество выпускаемых изделий.
